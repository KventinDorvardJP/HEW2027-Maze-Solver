# Unity-Python Protocol - Version 0.3

**Status: Draft for team review.** This document proposes the contract; it does
not mean these endpoints are implemented or that the team has approved it.

## 1. Purpose and ownership

Unity sends observations to Python. Python asks the local Ollama model
(`llama3.2:3b`) for a move and validates its response. Unity checks the requested
move against the actual maze, applies it if allowed, and reports the result.

- Backend base URL: `http://127.0.0.1:8000`.
- Request and response bodies use JSON (`Content-Type: application/json`).
- Version 0.3 uses a fixed 10 x 10 maze with walls, floor, start, and goal.
- Unity owns the maze, position, collision checks, reset, and goal detection.
- The LLM chooses moves. Errors never authorize a scripted or random fallback.
- The model never receives the full hidden map or a precomputed route.

## 2. Coordinates and observations

- `(0, 0)` is the bottom-left tile.
- `x` increases to the right; `y` increases upward.
- In-bounds coordinates are integers from `0` to `9` inclusive.
- A move must be orthogonally adjacent:
  `abs(destination.x - position.x) + abs(destination.y - position.y) == 1`.
- `nearby` contains exactly the four adjacent coordinates, in any order.
- Neighbor tile values are `floor`, `wall`, `goal`, or `out_of_bounds`.
- Include out-of-bounds neighbors with their actual coordinates, such as `x=-1`.
  Only these observations may contain coordinates outside the maze.
- The start tile is observed as `floor`; its coordinate is supplied separately.
- The example start and goal below illustrate the format. Unity supplies the
  fixed coordinates chosen for the prototype.

## 3. Health check

`GET /health` returns HTTP `200`:

```json
{"status":"ok"}
```

This confirms the Python API responds. It does not check Ollama or prove that
the navigation loop works.

## 4. Request a decision

`POST /decide`

```json
{
  "session_id": "example-run-001",
  "turn": 0,
  "start": {"x": 1, "y": 1},
  "goal": {"x": 8, "y": 8},
  "position": {"x": 1, "y": 1},
  "nearby": [
    {"x": 1, "y": 2, "tile": "floor"},
    {"x": 2, "y": 1, "tile": "wall"},
    {"x": 1, "y": 0, "tile": "wall"},
    {"x": 0, "y": 1, "tile": "wall"}
  ],
  "previous_outcome": null
}
```

All fields are required. Coordinates and `turn` must be JSON integers, not
strings, booleans, or fractions. `session_id` is a nonempty string generated by
Unity, at most 128 characters (a UUID is recommended). Extra JSON fields are
rejected. Goal observations must match the supplied goal coordinate, and the
start is observed as floor.

- A new session begins at turn `0`, at `start`, with `previous_outcome: null`.
- Python creates in-memory history when it accepts a new session's first request.
- Start and goal must be distinct and remain fixed within a session.
- After Unity reports the outcome of turn `n`, its next decision request uses
  turn `n+1`, the reported position, and that same outcome as `previous_outcome`.
- Python checks that the sequence and previous outcome match its history.
- Unity requests no further decisions after reaching the goal.
- Only one decision may be pending per session.

### Successful decision response

HTTP `200`:

```json
{
  "session_id": "example-run-001",
  "turn": 0,
  "move": {"action": "move", "x": 1, "y": 2}
}
```

The model itself must produce exactly the move object:

```json
{"action":"move","x":1,"y":2}
```

Python rejects malformed JSON, missing or extra move fields, actions other than
`move`, non-integer coordinates, out-of-bounds destinations, and nonadjacent
destinations. It wraps a valid move with the session and turn identifiers.

A `200` response is a requested move, not proof that movement succeeded.
Python does not replace a model-selected wall move with another move. Unity
independently validates every request and reports a blocked wall attempt.

## 5. Report the actual outcome

`POST /outcome`

Unity reports every executed decision, including blocked attempts and the final
goal-reaching move. This endpoint ensures the final outcome is recorded even
when there will be no next decision request.

Example: the requested move succeeded.

```json
{
  "session_id": "example-run-001",
  "turn": 0,
  "outcome": {
    "success": true,
    "status": "moved",
    "position": {"x": 1, "y": 2},
    "reason": null
  }
}
```

HTTP `200` acknowledgement:

```json
{"session_id":"example-run-001","turn":0,"recorded":true}
```

Allowed outcome combinations:

| Status | Success | Actual position | Reason |
| --- | --- | --- | --- |
| `moved` | `true` | Requested destination | `null` |
| `blocked` | `false` | Unchanged | `wall` |
| `invalid_move` | `false` | Unchanged | `out_of_bounds` or `not_adjacent` |
| `goal_reached` | `true` | Goal coordinate | `null` |

For example, a wall rejection has this outcome object:

```json
{
  "success": false,
  "status": "blocked",
  "position": {"x": 1, "y": 1},
  "reason": "wall"
}
```

All outcome fields are required. `position` always means the actual position
after Unity's checks. `invalid_move` is a defensive Unity check; Python should
already reject those destinations before returning a move.

Python checks that an outcome refers to its pending decision and is consistent
with the table. Unity remains authoritative about actual walls and movement.
Unity waits for acknowledgement before requesting the next decision.

## 6. Errors and timeouts

Errors never include a move. Application errors use this shape:

```json
{
  "error": {
    "code": "ollama_timeout",
    "message": "The local model did not respond in time."
  }
}
```

| HTTP status | Error code | Meaning |
| --- | --- | --- |
| `422` | `invalid_request` | Request JSON or fields violate this contract |
| `409` | `session_conflict` | Unknown session, wrong turn, pending decision, inconsistent outcome, or completed session |
| `502` | `invalid_model_output` | Model output fails JSON or move validation |
| `502` | `ollama_error` | Ollama returns an unsuccessful or unusable API response |
| `503` | `ollama_unavailable` | Python cannot connect to Ollama |
| `504` | `ollama_timeout` | Ollama exceeds the decision timeout |
| `500` | `internal_error` | Unexpected backend failure |

Implementation must normalize FastAPI request-validation errors to this error
shape. Messages are for display; clients use the code for classification.

- Ollama request timeout: 60 seconds total (implemented by the backend).
- Proposed Unity decision request timeout: 75 seconds total.
- Proposed Unity health/outcome request timeout: 10 seconds total.
- Unity performs HTTP requests without blocking its main game loop.
- On API errors, connection failures, malformed responses, or timeouts, Unity
  stops requesting decisions and displays the error. A decision error causes
  no movement. If outcome reporting fails, an already-applied move remains.
- Version 0.3 has no automatic retries. After an error, the user resets to start
  a new session. Repeated turns or duplicate outcome submissions return `409`.
  This avoids executing an uncertain decision twice.

## 7. Reset and history

- Reset stops the run, returns Unity to the fixed start, clears its visible run
  log, and creates a new session ID with turn `0`.
- Cancel old requests where possible. Always ignore responses whose session ID
  no longer matches the active run. Do not apply an old decision after reset.
- Python keeps histories isolated by session ID. A new session starts with no
  explored knowledge from previous runs.
- For this prototype, histories are in memory and lost when Python restarts.
  After a backend restart, Unity must reset before continuing an existing run.
- A reset does not need a backend endpoint: the next `/decide` starts the new
  session. Old histories may remain until the backend restarts.
- Python records observations, raw model responses, validated requested moves,
  actual outcomes, and errors. Prompt history preserves useful explored tiles
  and blocked attempts within the active session.
- For inference, Python summarizes all observed tiles and actual visit counts,
  and includes the eight most recent turns. It supplies walkable neighbors from
  the current observation without ranking or choosing a destination. Full run
  records remain in session history. Ollama's output schema offers all adjacent
  in-bounds coordinates (including wall attempts); geometry validation remains
  mandatory even when constrained generation is used.
- Unity's visible log shows the turn, requested destination, actual outcome and
  position, or error. A failed model response is never logged as a valid move.

## 8. Implementation acceptance checklist

Use this list for manual end-to-end acceptance. Automated results and actual
live checks are recorded in `docs/unity-verification.md`; an unchecked item
here does not imply that its underlying implementation is absent.

- [ ] Health returns the documented response.
- [ ] A real Ollama decision passes through Python to Unity.
- [ ] A legal move changes position by exactly one orthogonal tile.
- [ ] A wall attempt leaves position unchanged and records `blocked`.
- [ ] Malformed or invalid model output produces an error without movement.
- [ ] The final goal outcome is recorded and further decisions stop.
- [ ] Ollama/backend outages and timeouts are visible and stop the run safely.
- [ ] Reset begins at the start with fresh history and ignores old responses.
- [ ] Decision/outcome logs reflect actual requests and results.
- [ ] Only local observations and explored history reach the model.

Python endpoints and the Unity prototype client are implemented against this
draft. Team review is still pending. The checklist above remains a list of
acceptance scenarios; see the verification records for checks actually run.
Automated backend checks are in `backend/tests/`; a real-model check is
`backend/smoke_decision.py`. Unity tests are in `unity/Assets/Tests/`, and demo
instructions are in `docs/unity-demo.md`.
Run the backend with one worker because histories are process-local. Histories
are not persisted or automatically pruned in this prototype.

Ollama API references: [chat endpoint](https://docs.ollama.com/api/chat) and
[structured outputs](https://docs.ollama.com/capabilities/structured-outputs).
